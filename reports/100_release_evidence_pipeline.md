# Release Evidence Pipeline

## Current / Post-generation Phase Closure (2026-07-19)

- The 10-stage registry is split into five `current_decision_input` stages and five `post_generation_consumer` stages. Synthetic fixture corpus/replay and the retired Mature Readiness producer are no longer formal release inputs.
- The current source-contract gate is restricted to direct Native Audit. Catalog-managed/fallback stage identity is 4/6, and every stage has one explicit lifecycle owner and removal condition where fallback remains.
- No artifact was regenerated and no runtime DAG was executed; status remains `not run per user request`.

## Purpose

This report tracks `results/raw/native_release_evidence_pipeline.json`.

## Claim Boundary

This artifact aggregates existing evidence only. It does not execute product benchmark scripts, CUDA timing, native tests, endpoint probes, or final report rendering. Replay-ready and execute-ready decisions require target-machine artifacts under `results/raw/*.json`.

`cli_context` is input-contract metadata only. It records accepted JSON output mode, strict CLI validation, supported formats, and redacted path-probe status for release-pipeline inputs and output. It does not prove that refresh commands, validation, replay, execute, summary, Prometheus, or final report rendering ran.

Repair guidance is an implementation/debugging aid. It can suggest commands and ownership boundaries, but those commands are not considered run until their own refreshed artifacts exist.


Repair path groups and group plans are also review-only. They prioritize and summarize existing repair paths for operator navigation; they do not execute grouped commands, refresh artifacts, create benchmark evidence, or change the release decision by themselves.

Catalog-flow release repair paths are also review-only. They explain that catalog/new-artifact-flow wiring should be repaired and refreshed before release claims; single-source repair/parity counters plus surface, surface-consumer migration, fallback-removal queue state/next-action fields, fallback-removal shortest-path fields, fallback-removal parity-gate fields, root-cause fallback-removal shortest-path fields, root-cause fallback-removal parity-gate fields, and consumer field-coverage counters make fallback cleanup, fallback-removal blockers, downstream consumer refresh needs, missing registry fields, and current-repo versus target-machine action ownership visible. `catalog_flow_field_coverage_repair_path_count` specifically tracks Evidence Query consumer field-coverage gaps as release repair paths, `catalog_flow_fallback_removal_parity_gate_repair_path_count` tracks Evidence Query/root-cause parity-gate blockers as release repair paths, `catalog_flow_fallback_removal_shortest_path_repair_path_count` tracks root-cause shortest-path blockers as release repair paths, and `root_cause_catalog_flow_fallback_removal_parity_gate_repair_path_count` tracks the second-order root-cause parity-gate signal. These fields explain the first retained legacy surface and the environment split before fallback deletion. The nested `evidence_counters` array is a bounded explanation of why the path exists; it does not remove fallback lists, execute commands, refresh artifacts, or turn dry-run/replay metadata into benchmark evidence.

Catalog metadata-policy counters are weaker than catalog-flow repair paths. They show where registry entries still rely on derived defaults; they do not block release by themselves and do not prove or invalidate runtime evidence.


Evidence-query operation catalog closure is a read-only CLI contract. It documents supported query UX operations and their selector/target/snapshot requirements; it does not execute those operations, compare snapshot contents, refresh artifacts, or prove release readiness.

Evidence-query selector-resolution closure is read-only selector routing and repair-context metadata. It can expose ambiguous or missing selectors, source-location gaps, environment ownership, and bounded repair-card sample truncation for selector-specific repair paths, but it does not execute query operations, run repairs, refresh artifacts, or create benchmark/replay/execute evidence.

Evidence-query selector action plans are read-only triage guidance derived from existing selector resolution, repair cards, and readiness paths. They can suggest the next current-repo or target/validation step for release review, but they do not execute commands, mutate files, refresh artifacts, or prove that blockers were repaired.

Evidence-query selector repair-card external export status is also read-only metadata. A configured `--selector-repair-card-output` can write a full selector repair-card artifact for review, but that file is not proof that repairs, product replay, product execute, CUDA timing, or benchmark validation ran.

It forwards repair-card ownership counts for current repository, current validation server, target GPU/execute machine, and target product/replay evidence, plus source-location gap-card count, export review status, blocker reason, and whether a full external export file is still required. These fields explain selector export readiness only; they do not write repair results, refresh evidence, or prove release readiness.
